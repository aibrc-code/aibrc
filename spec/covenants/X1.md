# AIBTC Covenant Inscription · X1 Reference

**Stage: Live reference format.** X1 records a chain identifier and an external
contract address, giving Bitcoin assets a precise link to an external application.

## Why applications use X1

X1 gives a wallet or Agent a coordinate it can follow: which network and which
contract a project has referenced. Builders can use familiar EVM tools, ABIs and
RPC interfaces to inspect that contract's rules and state, then design a related
application interaction for the user.

For example, a community can reference a membership or game-service contract.
An assistant can find that service, explain its requirements and prepare an
interaction for approval. This connects Bitcoin asset discovery with existing
application infrastructure and leaves room for later execution and settlement
adapters. The [Smart Covenant guide](../../docs/04-smart-covenant.md) develops the
Agent uses; [cross-protocol applications](../../docs/05-cross-protocol.md) explains
how related assets and services can cooperate.

## Exact format declaration

The existing format declaration is reproduced verbatim:

```text
aibtc@X1:<decimal chainId>:<0x lowercase address>
```

Angle-bracket fields describe substitutions; they are not literal transaction
bytes. The resulting payload is one ASCII line, with no whitespace, BOM, newline,
leading zeroes in the chain ID, or appended fields. Its exact order is prefix,
chain ID and address, separated by colons.

## Current reference semantics

The input contains exactly `chainId` and `address`. The current format accepts
chain IDs `1`, `56`, `8453`, `42161`, `196`, and `4663`. The chain ID must be an
integer; the address must match `0x` followed by exactly 40 hexadecimal digits.
Input addresses are normalized to lowercase. Persisted canonical references
must already use that lowercase form. Neither a matching string nor an allowed
chain ID establishes that code exists or that a particular deployment is safe.

The complete payload is at most 57 bytes. A zero-value Bitcoin output carries
it as `OP_RETURN` followed by a minimal direct push of the complete ASCII line.
The prefix starts with `aibt`, not the `AIBR` state-instruction marker. The current
AIBRC Deploy / Transfer interpreter therefore does not execute an external
contract merely because this reference appears in the same Bitcoin transaction.

X1 and R1 are mutually exclusive reference modes. X1 does not select R1 fee
parameters, creator-fee routing, a buyback vault or buyback execution. It records
and displays the external reference; it performs no external-chain lookup,
bytecode verification or execution. The ordinary asset rules remain separate.

## Binding and absence of an immutable text artifact

The recorded pair is bound by the actual ASCII bytes included in the Bitcoin
transaction. X1 has no field for an external bytecode hash, an economic-text
hash, a reference build-manifest hash or proof that an external contract's
behavior matches an off-chain description. Bitcoin confirms the containing
transaction; it does not certify the external contract's semantics.

Unlike R1, the available frozen source material does not contain a separate X1
immutable economic-text artifact or an X1 text-hash constant. The format above
is an exact existing declaration. The surrounding explanation is an English
reference summary of that format, not a newly invented frozen contract text.
No deployed external address is selected by this document.
