# Glossary

| Term | Meaning |
| --- | --- |
| **Covenant Inscription** | AIBRC's name for its native assets and declarative on-chain representation. Their ownership is recorded as balances on script-derived accounts. AIBRC is the protocol; Covenant Inscription names the native asset expression. |
| **Shared-root issuance** | Parallel issuance paths under different asset standards, rooted in a common Bitcoin transaction. It gives the resulting artifacts a verifiable shared origin; each path retains its own validity and confirmation conditions. Also described as shared-origin issuance. |
| **Unified protocol** | Shared instruction, validity and state rules that independent implementations can interpret consistently. |
| **Shared application language** | Common asset identities, account concepts and interaction interfaces for wallets, applications and Agents, with each participating protocol's own rules preserved. |
| **Bitcoin–Agent double helix** | The vision of Bitcoin's money and verifiable history reinforcing an economy of useful Agent services, payments, receipts and operating budgets. |
| **Account abstraction** | The asset model separates balances and protocol authority from Bitcoin's UTXO inventory. **Balances live on script-derived accounts; authority is a protocol rule.** This phrase does not import an Ethereum execution standard, smart-contract VM or gas-sponsorship mechanism. |
| **Script account** | An AIBRC account identified by `TaggedHash("AIBRC/account/v1", scriptPubKey)`. The actual locking-script bytes are authoritative. An address is a wallet's encoding of a destination; it is not the balance record or an independent authorization rule. |
| **Authority** | The protocol's conditions for accepting an operation, including its designated authorization input and supported Bitcoin authorization shape. Possessing an application login or a readable account identifier does not supply that authority. |
| **Authorization input** | The transaction input selected by the instruction's index field. Its resolved previous-output script identifies the relevant sender or deploy authorizer. It is not necessarily the first transaction input, and it need not be the fee-only input. |
| **Canonical chain** | The valid Bitcoin history accepted under the node's chain-selection rules. A competing branch is not the current chain merely because somebody has observed it. Applications and indexers must identify the actual chain context of their answers. |
| **Canonical state** | The deterministic asset state derived by applying the specified rules to the canonical transaction order. Its serialized form contains assets, names, locators and positive balances in the defined order. A query projection is not a substitute for this state. |
| **State hash** | The current `SHA256(canonical_state_bytes)` fingerprint. It commits to the exact canonical JSON bytes defined by the specification. It is not the Proposed Merkle root and does not by itself provide local membership proofs. |
| **Asset ID** | The stable identity derived from the asset's network, deployment transaction's display-order bytes, owner output index and canonical name bytes under the specified tagged-hash rule. A ticker alone is not an Asset ID. |
| **Asset locator** | The compact `(blockHeight, txIndex)` reference used by Transfer to resolve an asset in the **current canonical chain**. It is not a second name for a deploy transaction hash. Following a reorganization, resolve it against the new canonical history rather than assuming an old interpretation survives. |
| **Deploy** | The current instruction that creates a named fixed-supply asset and assigns the initial supply to the script account derived from the designated owner output. Its validity includes network, name, supply, output and authorization checks. |
| **Transfer** | The current instruction that debits one authorizing script account for one asset and credits its allocation recipients. Validity is checked for the complete instruction; it does not partially apply an otherwise invalid allocation list. |
| **Allocation** | A recipient output index and a quantity for the referenced asset. There are at most 25 allocations, subject also to the payload-byte limit. BTC value carried by that output and its AIBRC quantity are separate values. |
| **Smallest unit** | The integer quantity used in supply and balance arithmetic. AIBRC uses eight display decimals. Supply `1` means one smallest unit, displayed as `0.00000001`, not one automatically standardized NFT. |
| **OP_RETURN marker** | The recognized `AIBR` marker in the required first-push structure. Extraction and envelope classification precede state application. A recognized malformed marker still participates in duplicate-marker classification. |
| **NO_OP** | A classification or application outcome in which the AIBRC instruction does not change state. The containing Bitcoin transaction may still be valid, confirmed and fee-paying. |
| **NEEDS_UPGRADE** | The result used when supplied activation context requires a version the implementation does not support. It must not be treated as permission to apply the older interpretation and keep announcing current state. |
| **Name policy** | The explicit context used to validate canonical name bytes. The current package supports its defined name-policy schedule; this is not a generic framework that activates arbitrary future instructions. |
| **Activation height** | The block boundary at which a defined interpretation is intended to become applicable under a complete network/version policy. The maintained value is `genesisHeight` in [config/release.json](../config/release.json), `null` until selected. Current Name Policy V2 activation derives from the same value. Numeric vector heights are synthetic test contexts. |
| **`activatedVersions`** | A codec classification input describing versions that the caller says are active. It is not network coordination, an activation announcement or an implementation of those future versions. |
| **Grant** | **Proposed.** An explicit bounded authorization under [AIP-0001](../proposals/AIP-0001-delegation-v1.md), with its own identity, owner permission-generation context, total remaining allowance and height limits. It is not ownership of the owner's full balance or a periodic budget. |
| **Agent Key** | **Proposed.** A delegate's working key under an owner-approved grant for a specified asset, remaining total allowance and height interval. It lets an Agent or other delegate act without receiving the owner key. Defined by AIP-0001; distinct from an application login or wallet session. |
| **`grantId`** | **Proposed.** The identifier distinguishing a particular grant from another grant or old authorization material. Its exact format belongs to the proposal and subsequent specification process. |
| **`ownerPermitNonce`** | **Proposed.** An owner's permission-generation sequence in the delegation design. It is not a BTC UTXO identifier or a general transaction fee nonce. Canonical ordering and confirmed revocation determine its effects. |
| **Lock** | **Proposed.** A rule restricting availability of a defined asset amount under specified conditions. An AIBRC lock does not automatically restrict native BTC controlled by an unrelated Bitcoin script. |
| **Attestation** | **Proposed.** An attributable typed statement. It identifies what an issuer states and its context; it does not make the statement's off-chain subject matter automatically true. |
| **Checkpoint** | **Proposed.** A contextual statement about a block, rules and state commitment. Signatures identify endorsers. A client still needs a policy for why that statement is an acceptable starting point. |
| **Merkle proof** | **Proposed reference format.** A path proving membership or non-membership relative to an accepted root. The reference uses a 256-level sparse tree; the uncompressed 256 sibling hashes occupy about 8 KiB before other fields. Correct path verification is separate from trusting the root. |
| **OTS / timestamp anchor** | A way to prove that committed bytes existed before an anchoring boundary. It does not prove asset backing, current chain membership of an unrelated deposit or correctness of every application action committed by those bytes. |
| **Smart Covenant** | AIBRC's programmable-rule framework: explicit rule identity, parameters, authority, execution context and checkable results. R1 identifies an application template; X1 identifies an external reference. Proposed authority and settlement rules extend the design without introducing a general-purpose Bitcoin VM. |
| **R1** | AIBTC Covenant Inscription R1: the published immutable rule-text identifier and economic semantics described in [the R1 reference](../spec/covenants/R1.md). A rule text, its binding and the actual executor have distinct responsibilities. |
| **X1** | AIBTC Covenant Inscription X1: the published external-reference semantics described in [the X1 reference](../spec/covenants/X1.md). Referencing another contract does not make Bitcoin execute it or make the referenced asset redeemable on demand. |
| **PSBT** | A partially signed Bitcoin transaction collaboration format. It helps participants prepare and sign exact Bitcoin material. It does not independently validate every embedded protocol leg or lock a script account's future balance. |
| **SIGHASH_SINGLE** | A Bitcoin signature mode that commits to the corresponding output under the applicable signature rules rather than every output. In the documented block-exchange design, the user's input uses SINGLE; the lane authorization input uses DEFAULT. This is not a blanket relaxation of core AIBRC authorization rules. |
| **SIGHASH_DEFAULT** | Taproot's default signature mode, with the full-output commitment of the relevant default signing semantics. In the documented block-exchange design, the lane's DEFAULT signature covers the complete transaction outputs. A valid 64-byte key-path signature implies DEFAULT; an explicit 65-byte signature ending in `00` is not the same valid encoding. |
| **Key path / script path** | Taproot spending forms distinguished after handling a possible annex. The current AIBRC authorization interpretation accepts its supported key-path shapes; script-path witness arguments must not be mistaken for a key-path signature merely because their length resembles one. Bitcoin still verifies signatures and script execution. |
| **UTXO / input** | A UTXO is an unspent Bitcoin output. Spending one makes it one transaction input. Combining several UTXOs normally creates several inputs; it does not collapse them into one input without another Bitcoin transaction. Script-account asset balances are a different accounting model. |
| **RFQ** | Request for quote: a request for a specific exchange that providers answer with explicit quantities, conditions and expiry. A quote, its signed transaction and confirmed delivery are different stages. |
| **Atomicity** | All-or-nothing behavior within a specifically defined system. Bitcoin transaction atomicity is not proof that every asset protocol instruction in it is valid. A cross-protocol settlement claim must establish each required leg and its interaction. |
| **Resident Agent** | **Research.** A service with continuous identity, an explainable treasury, bounded operating authority and recoverable content or memory commitments. Its model computation remains off-chain. |
| **Living Asset** | **Research.** A transferable asset relationship linked to a versioned service and explicit operating handover. A token Transfer alone does not move all external credentials, licenses or responsibilities. |
| **Live** | A rule or component implemented in the current referenced core, or explicitly identified current application tooling. It does not mean every possible product using that component is deployed, audited or proven at a particular capacity. |
| **Proposed** | A concrete direction documented as a proposal or reference design. Fields, activation and behavior are not silently promoted to current consensus rules. |
| **Research** | A direction that still requires important design choices, proof of properties, infrastructure or evidence of useful demand. It is neither a current feature nor a promise of a release date. |

For application examples, follow [the application map](07-applications.md). For the difference between a record commitment, rule validity and economic delivery, use [the extensions chapter](08-extensions.md) together with the [cross-protocol settlement discussion](05-cross-protocol.md).
